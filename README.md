# Чат с внешним API

Простое клиент-серверное приложение на Go с веб-интерфейсом на HTML/CSS/JavaScript.

## Возможности

- Веб-страница с текстовым полем для ввода сообщений.
- Введённое сообщение отображается сверху, ответ от внешнего API — снизу.
- Поддержка авторизации: `Authorization: Bearer`, `X-API-Key`, `Api-Key`.
- Два формата внешнего API:
  - **generic** — отправляет `{"message": "..."}`;
  - **openai** — отправляет запрос в формате `/v1/chat/completions`.
- LLM-агент в пакете `internal/agent` с расширяемой архитектурой (история, инструменты).
- Хранение истории диалогов в JSON-файлах по `session_id`.
- Кнопка очистки истории в веб-интерфейсе и endpoint `POST /api/chat/clear`.
- Настройка промптов: `SYSTEM_PROMPT`, `ASSISTANT_PROMPT`, `USER_PROMPT_TEMPLATE`.
- Панель управления в веб-интерфейсе: роль, формат ответа, температура, ограничение по длине, стоп-последовательность.
- Отображение времени ответа и использованных токенов под сообщением API.
- Накопление и отображение суммарного количества токенов за всю сессию (`session_total_tokens`).
- Стратегии управления контекстом:
  - `full` — полная история;
  - `summary` — 2 последних сообщения + summary остальной истории, сгенерированное LLM;
  - `sliding_window` — только последние 10 сообщений;
  - `facts` — к истории добавляется блок facts (ключ-значение), редактируемый в боковой панели;
  - `branching` — независимые ветки диалога с возможностью создавать ветки от текущей и переключаться между ними.
- Три уровня памяти агента:
  - **Краткосрочная** — текущий диалог внутри сессии/ветки;
  - **Рабочая** — данные текущей задачи в рамках проекта;
  - **Долгосрочная** — профиль проекта: технологии, паттерны, принципы, знания.
- Поле **Project ID** в боковой панели; при смене проекта генерируется новая сессия.
- Панель управления памятью проекта с CRUD-операциями для долгосрочной и рабочей памяти.
- Кнопки быстрого сохранения сообщений чата в память проекта.
- Авто-summary долгосрочной памяти при превышении 20 записей.
- Контекст проекта подаётся в LLM как отдельное системное сообщение.
- **Профили пользователей**: создание именованных профилей (имя + описание), переключение между ними в UI, участие описания профиля в каждом запросе к LLM как системное сообщение.
- **Инварианты проекта**: хранимые отдельно от диалога жёсткие правила (архитектура, технические решения, стек, бизнес-правила). Агент явно учитывает их в рассуждениях и на этапе `verification` workflow отказывается от решений, нарушающих `hard`-инварианты.
- **Конечный автомат задач**: каждый запрос может проходить этапы планирование → выполнение → проверка → завершение; каждый этап требует утверждения пользователя. Режим workflow можно включить переключателем в боковой панели; по умолчанию используется прямой режим chat.
- Логирование входящих HTTP-запросов и вызовов внешнего API.

## Хранение настроек

Настройки разделены на два файла:

- `.env.secrets` — чувствительные данные: `EXTERNAL_API_URL` и `API_KEY`. **Не коммитится**.
- `.env` — общие настройки: промпты, формат API, тип авторизации, порт. **Коммитится**.

При первом клонировании репозитория создайте `.env.secrets` из примера и заполните своим URL и ключом:

```bash
cp .env.secrets.example .env.secrets
```

## Запуск

### Через скрипт (рекомендуется)

```bash
./run.sh
```

Скрипт последовательно загружает `.env.secrets`, затем `.env`, и запускает сервер.

### Вручную

```bash
set -a
source .env.secrets
source .env
set +a
go run main.go
```

### Скомпилированный бинарник

```bash
go build -o ai-chat .
set -a
source .env.secrets
source .env
set +a
./ai-chat
```

После запуска откройте: http://localhost:8080

## Логирование

Сервер пишет в stdout следующие события:

- старт сервера и текущие настройки;
- каждый входящий HTTP-запрос с методом, путём, статусом ответа и временем выполнения;
- каждый вызов внешнего API с параметрами запроса и результатом (статус, длительность, `finish_reason`, длина ответа).

## Панель управления в веб-интерфейсе

В левой части страницы находится панель с элементами:

1. **Профиль** — выбор профиля пользователя.
2. **Режим обработки** — переключатель `chat` / `workflow`. В режиме `chat` ассистент отвечает сразу, в режиме `workflow` каждый запрос проходит четыре этапа с утверждением.
3. **Роль** — выпадающий список (`analyst` / `developer` / `tester`). Выбранная роль добавляет соответствующий системный промпт из `roles.yaml`.
4. **Формат ответа** — выпадающий список (`text` / `json`). При выборе `json` внешнему API отправляется параметр `response_format: {"type": "json_object"}`.
5. **Температура** — числовое поле (0–2). Отправляется как `temperature`.
6. **Ограничение по длине ответа** — числовое поле. Отправляется как `max_tokens`.
7. **Условие завершения ответа** — текстовое поле. Отправляется как `stop`.

Эти параметры передаются вместе с каждым сообщением.

## Примеры запуска без .env

### OpenAI-совместимый API

```bash
EXTERNAL_API_URL=https://api.ai.localcorp.net/v1/chat/completions \
API_KEY=sk-... \
AUTH_TYPE=bearer \
API_FORMAT=openai \
go run main.go
```

### Системный промпт и шаблон пользователя

```bash
EXTERNAL_API_URL=https://api.ai.localcorp.net/v1/chat/completions \
API_KEY=sk-... \
API_FORMAT=openai \
SYSTEM_PROMPT="Ты эксперт по Go. Отвечай кратко." \
USER_PROMPT_TEMPLATE="Вопрос про Go: {message}\nКраткий ответ:" \
go run main.go
```

### Простое внешнее API без авторизации

```bash
EXTERNAL_API_URL=https://httpbin.org/anything \
AUTH_TYPE=none \
API_FORMAT=generic \
go run main.go
```

## Проверка

```bash
curl -s -X POST http://localhost:8080/api/chat \
  -H "Content-Type: application/json" \
  -d '{"message":"Привет"}'
```

Очистка истории:

```bash
curl -s -X POST http://localhost:8080/api/chat/clear \
  -H "Content-Type: application/json" \
  -d '{"session_id":"your-session-id"}'
```

Получить память проекта:

```bash
curl -s 'http://localhost:8080/api/memory?project_id=my-project'
```

Добавить запись в память проекта:

```bash
curl -s -X POST http://localhost:8080/api/memory \
  -H "Content-Type: application/json" \
  -d '{"project_id":"my-project","entry":{"type":"principle","title":"SOLID","content":"Принципы ООП"}}'
```

Создать профиль пользователя:

```bash
curl -s -X POST http://localhost:8080/api/profiles \
  -H "Content-Type: application/json" \
  -d '{"profile":{"name":"Разработчик","description":"Опытный Go-разработчик"}}'
```

## Память проекта и профили

Память проекта хранится в каталоге `memory/` (не коммитится) по одному JSON-файлу на проект. Профили пользователей хранятся в каталоге `profiles/` (не коммитится) по одному JSON-файлу на профиль.

- **Project ID** — осмысленное имя проекта; разрешены буквы, цифры, пробелы, дефисы и подчёркивания.
- Долгосрочная и рабочая память привязаны к `project_id` и разделяются между всеми сессиями/ветками проекта.
- При смене `project_id` в UI создаётся новая сессия, чат очищается и загружается память нового проекта.
- Долгосрочная память автоматически сворачивается в `summary`, если в ней больше 20 записей.

## API памяти

- `GET /api/memory?project_id=...` — получить память проекта.
- `POST /api/memory` — создать или обновить запись.
  - Тело: `{ "project_id": "...", "entry": { "type": "...", "title": "...", "content": "...", "tags": [...] } }`.
  - Если `entry.id` задан — обновление, иначе создание.
- `POST /api/memory/delete` — удалить запись.
  - Тело: `{ "project_id": "...", "entry_id": "..." }`.

## Инварианты проекта

Инварианты — это жёсткие правила проекта (архитектура, технические решения, ограничения стека, бизнес-правила), которые агент должен учитывать и не имеет права нарушать. Они хранятся отдельно от диалога в памяти проекта как YAML-список в записи `type: invariants_list`.

Формат одного инварианта:

```yaml
invariants:
  - title: "Используем PostgreSQL как единственную БД"
    description: "Никакие другие СУБД не допускаются для основного хранилища."
    category: stack              # architecture | technical_decision | stack | business_rule
    severity: hard               # hard | soft
    active: true
```

- Активные инварианты подаются в LLM как отдельное системное сообщение.
- В режиме `chat` агент учитывает их через промпт, но гарантированный отказ не реализован.
- В режиме `workflow` на этапе `verification` агент явно проверяет результат по каждому инварианту; при нарушении `hard`-инварианта ответ начинается со строки `Отказ:`.

### API инвариантов

- `GET /api/invariants?project_id=...` — получить активные инварианты проекта.
- `POST /api/invariants` — сохранить список инвариантов.
  - Тело: `{ "project_id": "...", "invariants": [{ "title": "...", "description": "...", "category": "...", "severity": "hard|soft", "active": true }] }`.
- `POST /api/invariants/delete` — удалить все инварианты проекта.
  - Тело: `{ "project_id": "..." }`.

## API задач (конечный автомат)

По умолчанию запросы к `POST /api/chat` обрабатываются в режиме `chat` и возвращают прямой ответ. Если в запросе передать `"workflow_mode": "workflow"`, запускается задание с этапами:
- `planning` — планирование;
- `execution` — выполнение;
- `verification` — проверка на соответствие правилам проекта, профилю пользователя и инвариантам проекта;
- `completion` — завершение.

В режиме `workflow` LLM получает системное сообщение с описанием 4 этапов и правилом: переход на следующий этап возможен только после явного утверждения пользователя. Переходы между этапами контролируются сервером через endpoint’ы `approve` / `reject`.

Поле `workflow_mode` сохраняется в сессии и применяется ко всем последующим запросам, пока не будет изменено.

Endpoint’ы управления:

- `POST /api/task/approve` — утвердить текущий этап и перейти к следующему.
  - Тело: `{ "session_id": "...", "context_strategy": "..." }`.
- `POST /api/task/reject` — отклонить текущий этап и попросить переделать.
  - Тело: `{ "session_id": "...", "reason": "...", "context_strategy": "..." }`.
- `POST /api/task/cancel` — отменить текущее задание.
  - Тело: `{ "session_id": "..." }`.

## API профилей

- `GET /api/profiles` — список всех профилей.
- `POST /api/profiles` — создать или обновить профиль.
  - Тело: `{ "profile": { "id?": "...", "name": "...", "description": "..." } }`.
  - Если `id` не задан — создаётся новый профиль.
  - Возвращает `{ "profile_id": "...", "profiles": [...] }`.
- `POST /api/profiles/delete` — удалить профиль.
  - Тело: `{ "profile_id": "..." }`.

Активный профиль передаётся в `POST /api/chat` через поле `profile_id`.

## MCP-инструменты

Приложение поддерживает подключение внешних инструментов через [Model Context Protocol](https://modelcontextprotocol.io/) (stdio-транспорт).

### Конфигурация

Создайте файл `mcp.yaml` в корне проекта (он уже добавлен в `.gitignore`). Пример:

```yaml
servers:
  filesystem:
    type: stdio
    command: uvx
    args:
      - "-y"
      - "@modelcontextprotocol/server-filesystem"
      - "/Users/iguryanov"
    timeout: 30s
  fetch:
    type: stdio
    command: uvx
    args:
      - "-y"
      - "@modelcontextprotocol/server-fetch"
    timeout: 30s
  deepwiki:
    # DeepWiki использует Streamable HTTP транспорт, а не SSE.
    # Заголовок Accept: application/json, text/event-stream выставляется автоматически.
    type: http
    url: https://mcp.deepwiki.com/mcp
    timeout: 30s
```

Поля:
- `type` — тип транспорта: `stdio` (по умолчанию), `sse` или `http` (streamable HTTP).
- Для `stdio`:
  - `command` — исполняемый файл.
  - `args` — аргументы командной строки.
  - `env` — дополнительные переменные окружения для процесса сервера.
- Для `sse` и `http`:
  - `url` — URL remote MCP-сервера.
  - `headers` — произвольные HTTP-заголовки (например, `Authorization`).
- `disabled` — если `true`, сервер не запускается.
- `timeout` — таймаут вызова инструмента, по умолчанию `30s`.

### Использование

- Инструменты автоматически передаются LLM в формате OpenAI function calling, когда `API_FORMAT=openai`.
- Имена инструментов префиксируются именем сервера: `filesystem_read_file`.
- В режиме `chat` агент выполняет встроенный цикл: LLM может вызвать инструмент, получить результат и сформировать финальный ответ.
- В режиме `workflow` инструменты не используются.
- История диалога сохраняет сообщения `assistant` с `tool_calls` и сообщения `tool` с результатами.

### Статус MCP в интерфейсе

В левой панели веб-интерфейса отображается секция **MCP серверы**:

- Цветной индикатор состояния каждого сервера (зелёный — подключён, красный — ошибка, серый — отключён).
- Текст ошибки подключения, если сервер не удалось запустить.
- Раскрывающийся список инструментов с описанием.
- Кнопка **Обновить** для повторной загрузки статуса и списка инструментов.

Backend предоставляет endpoint:

```bash
curl -s http://localhost:8080/api/mcp/status
```

Ответ:

```json
{
  "servers": [
    {
      "name": "filesystem",
      "connected": true,
      "disabled": false,
      "error": "",
      "tools": [
        {
          "name": "read_file",
          "description": "Read a file from the filesystem",
          "parameters": { "type": "object", "properties": { ... } }
        }
      ]
    }
  ]
}
```

### Ограничения

- Поддерживается только stdio-транспорт.
- Работает только с OpenAI-совместимым форматом (`API_FORMAT=openai`).
- Если MCP-сервер не удалось запустить, приложение продолжает работу без его инструментов.

## Структура

- `main.go` — точка входа, создание агента и запуск HTTP-сервера.
- `config.go` — загрузка конфигурации сервера и YAML-файлов.
- `handlers.go` — HTTP-обработчики.
- `logger.go` — middleware для логирования.
- `models.go` — HTTP-модели запроса/ответа.
- `internal/agent/` — пакет LLM-агента:
  - `agent.go` — интерфейс `Agent` и реализация `SimpleAgent`;
  - `client.go` — HTTP-клиент для внешнего API;
  - `config.go` — конфигурация агента;
  - `invariants.go` — форматирование инвариантов проекта в системный промпт;
  - `payload.go` — построение JSON-запроса;
  - `prompts.go` — построение системного промпта и сообщений;
  - `extract.go` — разбор ответа внешнего API;
  - `types.go` — модели агента.
- `internal/history/` — хранение истории диалогов:
  - `store.go` — интерфейс `Store` и файловая реализация `FileStore`.
- `internal/memory/` — хранение памяти проекта:
  - `store.go` — интерфейс `Store`, файловая реализация `FileStore` и вспомогательные функции;
  - `invariants.go` — типы и функции для работы с инвариантами проекта.
- `internal/profile/` — хранение профилей пользователей:
  - `store.go` — интерфейс `Store`, файловая реализация `FileStore` и вспомогательные функции.
- `internal/mcp/` — MCP SDK клиент:
  - `config.go` — загрузка `mcp.yaml`;
  - `client.go` — обёртка над stdio MCP-клиентом;
  - `registry.go` — реализация `agent.ToolRegistry` для нескольких серверов.
- `static/index.html` — веб-интерфейс чата.
- `.env.secrets` — чувствительные данные (не коммитится).
- `.env.secrets.example` — пример секретов (коммитится).
- `.env` — общие настройки (коммитится).
- `mcp.yaml` — конфигурация MCP-серверов (не коммитится).
- `mcp.yaml.example` — пример конфигурации MCP-серверов (коммитится).
- `orchestrator.yaml` — базовые инструкции оркестратора (коммитится).
- `roles.yaml` — роли для системного промпта (коммитится).
- `run.sh` — скрипт запуска.
- `.gitignore` — исключает секреты, историю, память и `mcp.yaml` из репозитория.
