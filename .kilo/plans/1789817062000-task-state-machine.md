# План: Конечный автомат задач в сессии

## Цель
Каждый пользовательский запрос в чате проходит через этапы: **планирование → выполнение → проверка → завершение**. Каждый этап требует явного утверждения пользователя. При отклонении этап повторяется с учётом причины; на этапе проверки LLM сам проверяет соответствие правилам проекта и профиля.

## Принятые решения
- Состояние конечного автомата хранится в сессии (`internal/history.Session`) в полях `task_stage`, `task_status`, `task_context`.
- Конечный автомат применяется к каждому пользовательскому запросу автоматически; новое сообщение пользователя сбрасывает состояние в `planning`.
- Утверждение/отклонение происходит через кнопки под ответом ассистента на каждом этапе + поле для причины отклонения.
- Пока этап не утверждён, поле ввода нового сообщения заблокировано.
- При отклонении агент остаётся на том же этапе и перегенерирует результат с учётом причины.
- На этапе **проверки** LLM явно сверяет результат с долгосрочной/рабочей памятью проекта и профилем пользователя; если найдено нарушение, он формулирует причину отклонения.

## Модель состояния

### Расширение `internal/history.Session`
```go
type Session struct {
    Strategy     string            `json:"strategy"`
    TotalTokens  int               `json:"total_tokens"`
    Facts        map[string]string `json:"facts"`
    Branches     map[string]Branch `json:"branches"`
    ActiveBranch string            `json:"active_branch"`
    TaskStage    string            `json:"task_stage,omitempty"`   // planning | execution | verification | completion
    TaskStatus   string            `json:"task_status,omitempty"`  // pending | approved | rejected
    TaskContext  TaskContext       `json:"task_context,omitempty"`
}

type TaskContext struct {
    OriginalRequest string            `json:"original_request"`
    Plan            string            `json:"plan,omitempty"`
    ExecutionResult string            `json:"execution_result,omitempty"`
    VerificationReport string         `json:"verification_report,omitempty"`
    CompletionSummary string          `json:"completion_summary,omitempty"`
    RejectionReason string           `json:"rejection_reason,omitempty"`
}
```

### Статусы и переходы
- `planning` → `execution` (после утверждения плана)
- `execution` → `verification` (после утверждения выполнения)
- `verification` → `completion` (после утверждения проверки)
- `completion` → завершение; сессия остаётся без активного задания (`task_stage` очищается)
- Отклонение на любом этапе: остаёмся на текущем этапе, `task_status = rejected`, сохраняем `rejection_reason`, перегенерируем вывод.

## Backend

### Изменения в `internal/history/store.go`
- Расширить структуру `Session` полями `TaskStage`, `TaskStatus`, `TaskContext`.
- `SaveSession` должен инициализировать `TaskContext`, если оно nil.

### Изменения в `internal/agent`
- `AgentRequest`:
  - Добавить `TaskAction string` (`"approve"`, `"reject"`, `""`).
  - Добавить `RejectionReason string`.
- `AgentResponse`:
  - Добавить `TaskStage`, `TaskStatus`, `TaskContext`.
- `SimpleAgent.Run`:
  - Загрузить сессию.
  - Если `req.Message` не пустой — сбросить task state: `task_stage = "planning"`, сохранить `original_request`.
  - Если `req.TaskAction == "approve"` — перевести на следующий этап.
  - Если `req.TaskAction == "reject"` — оставить на текущем этапе, сохранить причину отклонения.
  - Сгенерировать вывод текущего этапа через LLM.
  - Сохранить результат в `TaskContext`.
  - Вернуть `TaskStage`, `TaskStatus`, `TaskContext` в ответе.
- Промпты:
  - Добавить `buildTaskStagePrompt(stage, taskContext, projectContext, userProfileContext)`.
  - На этапе `verification` явно требовать проверки против долгосрочной/рабочей памяти и профиля.
  - При `task_status == rejected` включать `rejection_reason` и просить переработать вывод.
- `buildMessages`/`buildPayload`:
  - Добавить системное сообщение с текущим этапом и контекстом задания.
  - Сохранить существующий порядок: системный промпт → профиль → контекст проекта → контекст задания → история → сообщение пользователя.

### Новые HTTP endpoint’ы
- `POST /api/task/approve`
  - Тело: `{ "session_id": "...", "context_strategy": "..." }`.
  - Агент переходит к следующему этапу и генерирует вывод.
- `POST /api/task/reject`
  - Тело: `{ "session_id": "...", "reason": "...", "context_strategy": "..." }`.
  - Агент остаётся на текущем этапе и перегенерирует вывод с учётом причины.

### Валидация
- `POST /api/chat` остаётся основным способом начать новое задание.
- Если `task_status == pending`, входящее сообщение без `task_action` либо игнорируется, либо сбрасывает задание (новое сообщение = новый запрос). Рекомендуется: frontend блокирует ввод, поэтому ситуация маловероятна.

## Frontend

### UI состояния задания
- В боковой панели добавить блок **Задание** с текущим этапом и статусом:
  - «Планирование», «Выполнение», «Проверка», «Завершение».
  - Прогресс-бар или список этапов.
- При ожидании утверждения блокировать поле ввода сообщения (`input.disabled = true`) и показывать текст «Ожидается утверждение этапа».

### Кнопки утверждения в чате
- Для сообщений ассистента, сгенерированных в рамках задания, добавить кнопки:
  - «Утвердить и продолжить»
  - «Отклонить и переделать»
- При отклонении показывать текстовое поле для причины.
- Кнопки вызывают `POST /api/task/approve` или `POST /api/task/reject`.

### Обработка этапов
- После отправки сообщения пользователя:
  - Если ответ содержит `task_stage` — показать кнопки утверждения.
  - Заблокировать поле ввода.
- После утверждения/отклонения:
  - Обновить `task_stage`/`task_status` из ответа.
  - Если `task_stage == "completion"` и `task_status == "approved"` — разблокировать ввод, показать итоговое сообщение.
  - Иначе — показать новый результат и оставить кнопки.

### Сохранение состояния
- `task_stage`/`task_status` не сохраняются в `localStorage`, так как они хранятся в сессии на сервере.
- При загрузке страницы frontend запрашивает сессию? Сейчас сессия загружается только при отправке сообщения. Нужно ли загружать task state при старте?
  - Рекомендуется: при старте не загружать task state; если пользователь отправит сообщение, а сессия находится в pending, агент вернёт текущий этап с кнопками.
  - Альтернативно: добавить `GET /api/session/state?session_id=...` для получения текущего task state.

## Взаимодействие с памятью
- На всех этапах в LLM подаётся проектная память и профиль (как сейчас).
- На этапе `verification` добавляется явный системный промпт:
  - «Проверь результат предыдущего этапа на соответствие принципам, технологиям, паттернам и задачам проекта, а также профилю пользователя. Если есть нарушения, опиши их как причину отклонения. Если всё корректно, напиши 'Утверждено'.»
- При отклонении с пустой причиной verification-промпт сам формулирует причину.

## Backward compatibility
- Старые сессии без `task_stage` работают как раньше: сообщение обрабатывается напрямую, `task_stage` устанавливается в `planning` при первом новом запросе.
- Если пользователь отключит workflow (например, через настройку в будущем), `task_stage` игнорируется.

## Риски
- **Блокировка ввода**: если frontend не получит ответ или произойдёт ошибка, пользователь может остаться с заблокированным вводом. Нужна кнопка «Отменить задание».
- **Бесконечные циклы**: пользователь может многократно отклонять один этап. Для MVP допустимо; в будущем можно ограничить число попыток.
- **Размер контекста**: `TaskContext` накапливает вывод каждого этапа. При длинных результатах это увеличивает запросы. Для MVP допустимо.
- **Пересечение с ветками**: если пользователь переключает ветку во время задания, task state остаётся в сессии и применяется к новой ветке. Рекомендуется: task state общий для сессии, независимо от ветки.

4. Реализовать логику переходов этапов в `SimpleAgent.Run`.
5. Добавить `buildTaskStagePrompt` и обновить `buildMessages`/`buildPayload`.
6. Добавить endpoint’ы `POST /api/task/approve` и `POST /api/task/reject`.
7. Обновить `main.go` роутами.
8. Добавить в frontend блок состояния задания в боковой панели.
9. Добавить кнопки утверждения/отклонения под сообщениями ассистента.
10. Реализовать блокировку ввода и кнопку «Отменить задание».
11. Добавить unit-тесты для переходов состояний.
12. Проверить вручную полный цикл: запрос → планирование → утверждение → выполнение → проверка → завершение.
